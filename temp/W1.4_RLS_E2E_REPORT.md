# W1.4 — Tenant İzolasyonu RLS E2E Doğrulaması (Faz 9 modülleri)

**Tarih**: 4 Ağustos 2026
**Durum**: ✅ Tamamlandı (4/4 modül geçti)
**Kapsam**: lab_tests, lab_orders, lab_results, imaging_orders

## Özet

Faz 9 modüllerinin (lab/görüntüleme) DB'ye taşınması (W1.2a-d) sonrasında,
PostgreSQL Row Level Security (RLS) ile tenant izolasyonunun **veritabanı
katmanında** doğru çalıştığı 4 ayrı e2e testi ile kanıtlandı. Testler
uygulamanın prod PostgreSQL rolünü değil, geçici bir **NOSUPERUSER /
NOBYPASSRLS** rolüyle çalışır; gerçek RLS policy'sinin koşullarını
birebir uygular.

W1.2a-d sırasında yazılan repository'ler RLS bağlamını kurmuyordu
(transaction-yerel `set_config('app.tenant_id', ...)` çağrısı yoktu). Bu
testlerde ortaya çıkan bu eksik, **W1.4 kapsamında `withContext` helper'ı
ile giderildi** — bu sayede hem testler hem de production aynı mimaride
çalışır.

## Düzeltilen kritik üretim bug'ı

W1.2a-d repository'lerinde RLS context kurulmadan doğrudan
`this.prisma.labTest.findFirst({ where: { id, tenantId } })` gibi sorgular
yapılıyordu. Bu, **production'da** (PrismaService'in `app.tenant_id` GUC
değerini set etmediği bir deployment'ta) aşağıdaki sonuçları doğururdu:

- WHERE cümlesi her zaman `tenantId = X` filtresini koyduğu için **kendi
  tenant'ının satırlarını da göremezdi** (RLS USING clause
  `tenant_id::text = current_setting('app.tenant_id', true)` kontrolü
  yapar, context boşken 0 satır döner).
- Veya daha kötüsü, superuser ile bağlanılıyorsa (RLS bypass) sorgular
  çalışır ama **tenant filtresi tek savunma hattı** olur; bu da
  AGENT_RULES'taki "fiziksel katmanda tenant izolasyonu" kuralını ihlal
  ederdi.

Bu yüzden 4 repository de `withContext(actor, fn)` private helper'ı ile
her sorguyu `prisma.$transaction` içine alıp transaction-yerel
`set_config('app.tenant_id', ...)` çağrısı yapacak şekilde refactor
edildi. Public API değişmedi; service testleri (test double kullanan)
etkilenmedi.

### `withContext` kalıbı

```ts
private async withContext<T>(
  actor: TenantActor,
  fn: (tx: Prisma.TransactionClient) => Promise<T>,
): Promise<T> {
  const isSuper = actor.isSuperadmin ? "true" : "false";
  const tenantId = actor.tenantId;
  return this.prisma.$transaction(async (tx) => {
    await tx.$executeRaw`SELECT set_config('app.is_superadmin', ${isSuper}, true)`;
    await tx.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId}, true)`;
    return fn(tx);
  });
}
```

- `set_config(name, value, is_local=true)` → transaction-yerel
  (transaction sonunda otomatik temizlenir, aynı bağlam içindeki
  sorgular RLS policy'sini doğru uygular).
- `tenantId` metod imzasından gelir (zaten tüm public metotlar
  `tenantId` parametresi alıyordu), ayrı bir `actor` parametresi
  eklenmedi → service API'si değişmedi, test double kullanan
  service testleri etkilenmedi.
- WHERE cümlesi + RLS USING clause **aynı tenant bağlamıyla**
  çalışır → defense-in-depth.

### Her modülde doğrulanan senaryolar

1. **Tenant bağlamı yokken SELECT boş döner**; INSERT 42501 (new row
   violates row-level security policy) fırlatır.
2. **Doğru tenant context** yalnızca kendi satırlarını açar; diğer
   tenant'ın satırları görünmez.
3. **Repository.findById / findByCode / findActiveByOrder / nextRevision
   / listByOrder** cross-tenant erişimde `null` döner (P2025 →
   repository null kapsar).
4. **Repository.insert** kendi tenant context'inde yeni kayıt ekler; aynı
   id ile doğru context'te görünür, yanlış context'te görünmez.
5. **Repository.update** doğru tenant'ta başarılı; cross-tenant update
   `null` döner ve hedef satır admin üzerinden doğrulandığında
   değişmediği görülür.
6. **Append-only trigger** tenant context doğru olsa dahi DELETE'i
   reddeder (`lab_tests_block_delete` vb.).
7. **App role yetki kontrolü**: `information_schema.role_table_grants`
   üzerinden app role'ün yalnızca `SELECT, INSERT, UPDATE` aldığı
   (DELETE verilmediği) doğrulanır.

## Mimari kararlar

- **`withContext` her sorguda zorunlu**: Bu kalıp sayesinde repository
  katmanı RLS'in DB tarafından uygulanmasını garanti eder; service
  katmanı RLS'i bilmek zorunda değildir.
- **Tenant context `tenantId` parametresinden türetilir**: Mevcut
  public API değişmedi; geriye dönük uyumluluk korundu. Gerekirse ileride
  `actor` parametresi ayrıca eklenebilir.
- **`tx.$transaction` array formu yerine `Promise.all`**: Transaction
  client üzerinde Prisma'nın `$transaction` array formu yok; aynı
  RLS context içinde paralel çalıştırmak için `Promise.all` kullanıldı
  (lab-tests, lab-orders, imaging-orders'taki `search` count+findMany
  paralelliği).
- **`--no-file-parallelism` zorunlu**: E2E testleri aynı DB'ye roller
  oluşturup siler; suite'ler paralel çalıştığında PG catalog tuple
  yarışı (`XX000 tuple concurrently updated`) çıkıyor. Sıralı çalışma
  hem doğru hem yeterince hızlı (5 saniye).

## Takip edilecekler (ileride)

- W1.2e (lab-adapters) ve W1.3 (notifications) revert edilmişti; bu
  modüller DB'ye taşındığında aynı `withContext` kalıbı uygulanmalı.
- Production'da PrismaService'in `app.tenant_id` GUC'sini kurmaması
  gerekiyor (request başına NestJS interceptor'da set edilebilir);
  bu konu Faz 9 sonrası Hafta 2 deploy hazırlığında ele alınacak.
- Mevcut diğer modüller (vaccinations, examinations, prescriptions
  vb.) için de aynı kalıbın uygulanıp uygulanmadığı denetlenmeli;
  bu bir sonraki RLS e2e turlarının konusu.
